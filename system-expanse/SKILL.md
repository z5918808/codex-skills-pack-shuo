# SYSTEM-EXPANSE

把系統說清楚，再讓同一套邏輯成為工程規格。依使用者要求停在說明、規格或 goal 草案；不要因為載入本技能就啟動部署、建立 goal 或發布文件。

## 先核對事實

- 窄讀相關程式入口、既有規格、責任邊界與使用者已確認的決策，優先重用證據。
- 明確區分「已驗證現況」「目標設計」「未知條件」。規格寫好了、程式能啟動，都不等於端到端成功。
- 找到現有規則與狀態的唯一 owner；詳細規格引用原文，避免建立第二份會漂移的規則。
- 只對影響設計且無法由現有資料判定的缺口提問。合理推定要標示，不重問已確認事項。

## 用 ELI10 解釋同一套系統

先用幾句白話回答：誰使用、從哪裡進來、交給誰做、能碰哪些資料、結果回到哪裡。介紹術語時說明它負責的動作。

視複雜度提供：

- **拓樸圖**：用 Mermaid 畫真實必要的角色與通道，標明是現況或目標；箭頭說明傳的是任務、資料或通知。
- **分流表**：入口 → 經驗證身分／權限 → 處理者 → 資料／工具 → 回覆對象。
- **代表流程**：用一個具體請求走完進件到回覆，再補相關的離線、拒絕、逾時或重送情況。

圖、表與文字必須一致。不要為了畫圖增加服務；不要把品牌、系統邊界與部署位置混成同一層。

## 收斂工程決策

依實際需求檢查，不強制每個專案採用相同架構：

- 每項能力、資料與排程有明確 owner；沿用現有介面，只有已證實缺口才新增機制。
- 共用入口、主機或程式庫不自動代表共用資料、記憶、session、憑證或權限。
- 若有角色權限，說明在哪個程式邊界驗證可信身分，以及拒絕發生在讀取資料／憑證之前還是之後。
- 回覆綁定原任務、使用者與入口；若有模式切換，說明進行中任務如何避免串線。
- 說明必要的去重、逾時、保留、資源與回滾行為；只寫與本需求相關的條件。
- 依賴不可用時如實失敗，不以不同來源、舊資料或更大權限悄悄替代。

## 形成可驗收規格

使用者要求正式規格時，讀 [to-spec](../to-spec/SKILL.md) 的模板，沿用其文件結構與既有測試切點；這是查閱格式，不會啟動該技能或發布到 tracker。本技能補充拓樸與分流分析，不複製維護另一套 PRD 模板。

- 每個必要結果對應可觀察的驗收證據，涵蓋正常結果及相關權限／失敗路徑。
- 優先從既有入口驗證使用者行為；離線測試、實機測試與自然事件證據分開標示。
- 輸出需能讓讀者辨認目標、現況、未完成項目及下一個必要動作。
- 文件路徑與控制面更新遵循專案契約。發布到外部 tracker 依當次要求與既有授權，不由自動選用本技能推定。

使用者也要求 goal 時，讀 [prompt-for-goal](../prompt-for-goal/SKILL.md)，按獨立驗收結果分階段，直接引用正式規格；不要重抄完整規則或自動執行 goal。
