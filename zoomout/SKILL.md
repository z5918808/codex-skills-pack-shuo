# Zoom Out

從局部補洞回到使用者結果，找出限制主線的瓶頸，選一個最小可驗證的突破。先刪除與簡化，再考慮可重用機制、驗證與自動化。

## 1. 校正問題

將目前敘事分成已驗證事實、現有解釋及可能造成偏見的短期 context。近期錯誤、最新 diff／artifact、舊 handoff 都只是線索。先用一句話指出「哪個瓶頸限制哪個結果」，未證實就標假設。

定義本次高度：局部、模組或系統；以及目標、完成證據、可改／凍結範圍。只要策略或 review 就保持唯讀；要求實作才於授權內做最小增量。正式環境、DB、金流、訂單、庫存、客戶資料、憑證、破壞性或批量操作先走適用預檢與 gate。

## 2. 找決定性證據

讀最小系統地圖：輸入、輸出、主線、關鍵判斷／介面、state owner、驗收及恢復。查 repo、檔案、命令、測試、runtime、UI／API 或必要 preview；只讀能改變決策的內容。

掃一次使用者／operator、產品價值與範圍、權限、安全、state／writer、介面、驗收與恢復的盲點。盲點是待查問題，與「值得問的更好問題」分開，取得證據後才成為結論。

每次查證只需問題、證據目標、動作、結果及決策。支持就進下一步，反駁就換突破點，缺資料就縮小查證。

## 3. 先刪除，再排序

依序檢查需求、流程步驟、模組／文件／交棒、未確認限制、介面、重複狀態及人工工作。將問題分成症狀、反覆模式、缺少的可重用機制；保留一個擁有規則的來源。

固定改善順序：刪除 → 簡化 → 穩定介面 → 驗證 → 自動化 → 擴大。機制優先放在既有產品邊界與 owner，再選必要的驗證、command、恢復路徑或工作流；全域規則最後考慮。

按解除主線瓶頸、吸收反覆錯誤、提前／降低驗證成本、縮小介面、減少狀態同步、小步移植與風險排序。比較足以支持選擇的候選，只推薦一個先做；太大就切第一個能獨立驗證的薄片。

主要影響外觀、一次清理或不限制主線的修飾可延後。影響安全、信任、收入、法律、關鍵使用流程、正式正確性，或反映底層缺口者仍需優先處理。記錄延後理由，避免可見度取代證據排序。

## 4. 落地與驗收

選定方向需要新機制時，讀 [最低可用大工廠契約](references/minimum-factory.md)，定義重複工作、owner、input／output、第一版、驗證與停止條件。可直接刪除或簡化時沿現有 owner 處理。

提出方案或完成改動前，核對是否解到真正瓶頸、保留權限、先簡化、第一版足夠小、驗收獨立且剩餘風險清楚。有具體可處理問題就修正後重新核對；無決策相關問題時結束。

外部 review 前整理大局、原始證據、假設及要決策的問題。`report-for-outsourcing` 是明示入口，只有使用者已要求外部報告時才使用；正式傳送仍依接收者、內容及用途授權。

短回報判斷、context 偏見、待查盲點、真正瓶頸、建議動作、驗證與延後事項。多模組、多流程、反覆錯誤、高風險或要求完整分析時讀 [完整分析格式](references/full-report.md)。結果以一個可驗證修正判定；建立大制度、流程完整或摘要成功本身不足以完成。
