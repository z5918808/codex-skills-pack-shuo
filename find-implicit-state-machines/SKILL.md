# Find Implicit State Machines

把「find all of the implicit state machines in my app」轉成有程式證據的流程盤點。找出哪些狀態決定下一步可做什麼，以及事件如何改變它們；涵蓋相關前端、後端、背景工作與維運入口。

預設只分析並回覆，不改碼、建立報告檔、啟動服務或觸發外部副作用。使用者另外要求修復時，盤點結果作為修復依據，執行沿原任務授權。建立或修改本 skill 不啟動被分析專案的工作。

## 判斷範圍

- **隱含狀態機**：保留的歷史或目前狀態會改變後續事件的合法性、結果或副作用，轉換規則散落在欄位、條件與操作順序中。
- **部分明確化**：已有 enum、status 欄位或狀態名稱，但允許的轉換、重試或跨流程約束仍分散。另列並指出實際缺口。
- **衍生狀態**：可從當期輸入直接算出、沒有事件歷史的分類或呈現分支。只在它參與真正的狀態轉換時納入，不把每個 if、boolean 或錯誤回傳都算成狀態機。

依實際路由、註冊、設定及呼叫者確認可達性。區分現行、可選啟用、回退／相容與已停用流程；文件或舊測試不足以證明正在使用，checkout 分析也不證明線上實載。

## 追查方法

1. **建立涵蓋範圍。** 讀適用專案入口，辨識應用程式、第一方前端、schema／migration、工作佇列、排程與管理命令。全 app 請求先逐區域掃描，再深入候選；單一流程請求沿其上下游查，不擴成全庫審查。第三方、生成檔與歷史資料預設排除，必要時回查其第一方接線。
2. **搜尋候選並核對行為。** 除了 state/status/phase，也查 boolean 組合、null／資料列存在、token、revision、時間戳、重試次數、Promise／取消控制、DOM／ARIA／CSS class、cookie／storage、鎖與階段回執。搜尋只是線索；讀實際寫入點及消費者，避免以命名認定狀態。
3. **重建轉換。** 對每個成立的候選追出「目前狀態 + 事件 + 條件 → 下一狀態 + 副作用」。找到初始化、更新與終止／失效路徑，記錄狀態由誰持有、存在哪裡、能活多久。依該流程實際需要追重試、逾時、取消、重播、並行、重啟或回復，不假設所有流程都有這些轉換。
4. **核對邊界。** 查同一狀態的所有寫入者與讀取入口。獨立狀態維度保持分開，例如內容已保存不代表通知已送達，草稿已更新不代表公開快照已更新；也標出它們之間必須成立的約束。相同共用流程合併，語意不同的流程保留。
5. **對帳後交付。** 逐區域記下已掃描、排除與未追通的部分，對關鍵轉換核對呼叫路徑及既有契約／測試。唯讀原始碼足以回答時不啟動環境；只有實際執行過的路徑可標為動態驗證。

## 證據與風險

每個盤點項目至少交代用途、狀態、主要事件／條件、狀態載體與可定位的程式證據。重要的跨檔案流程同時引用更新處與判斷處；分析者自訂的狀態名稱須說明是整理名稱，不假裝程式已有這些型別。

檢查有證據的矛盾狀態、遺漏轉換、失效回應覆蓋新結果、重複副作用及中斷後無法接續。區分「程式已證實的缺陷」、「結構上的維護風險」與「待驗假設」，不要因為狀態隱含就宣稱存在 bug。

全量盤點的完成依據是已辨識入口與狀態載體的涵蓋對帳，以及候選已確認、合併或排除。列出搜尋與存取限制；部分讀取、截斷輸出或只搜 status 不能支持「全部找完」，必要時縮小查詢補齊缺口。

## 優化與第二輪架構審查

使用者要求優化、重構或架構審查時，採用 John Ousterhout《A Philosophy of Software Design》的「Deepen modules and simplify interfaces」原則：讓模組承擔完整且相關的行為，減少呼叫端必須理解的狀態細節。用於 PR 第二輪審查時，先沿第一輪功能正確性與相關驗收證據，再檢查模組深度；審查仍預設唯讀，不自行啟動重構或新增審查代理。

- **從呼叫端判斷深度。** 介面包含函式、參數、旗標、必要呼叫順序、錯誤及恢復規則。找出呼叫端必須自行編排初始化、驗證、轉換、持久化與副作用的淺層模組，引用實際呼叫點說明複雜度如何外洩。
- **集中同一責任。** 將重複的轉換條件與業務規則交回既有行為擁有者，以簡單且能表達結果的介面完成相關流程。保留獨立狀態維度、交易一致性、重試與結果不明的差異；不把保存成功包裝成通知已送達。
- **刪除無收益的間接層。** 檢查只轉傳的參數、包裝函式、重複設定與不必要抽象。每個修改須說明呼叫端少知道什麼、規則少重複在哪裡，或日後改動能集中在哪裡；只把八次呼叫藏進第九個函式，未改善責任與契約，不算完成。
- **控制整合範圍。** 優先沿既有模組整合相關責任；只有具體缺口才新增抽象。不合併語意不同的流程、不建立承包無關工作的巨大模組，也不為減少公開方法而隱藏必要錯誤、安全邊界或恢復能力。完整評估可以保留現狀。
- **依行為驗收。** 已授權修改時，從簡化後的正式介面驗證既有行為、契約、安全邊界及受影響的跨流程約束；沿適用 AGENTS.md 的 Outcome-first verification 重用相關測試，補驗具體缺口。單純移檔、函式減少或行數下降不能代替結果。

## 回覆方式

先說主要發現與分析範圍。用依使用者流程分組的表格列出「流程｜狀態與主要轉換｜狀態載體及程式位置」，將部分明確化、已停用與衍生狀態清楚區別。複雜流程才補轉換表或 Mermaid，不為每個開關畫圖。

最後列出重要跨流程約束、具體風險及未驗證邊界。若使用者要求優化建議，先依資料正確性、副作用與恢復成本排序，再提出最小修改；完整評估可得出保留現狀，不強制把每個流程改為 enum、導入狀態機函式庫或建立全域框架。

優化或架構審查另交代模組責任改善、消除的重複規則、介面前後差異，以及剩餘複雜度與回歸風險。建議與已實作成果分開；實作後附相關驗收證據，並以同一檔案範圍及計數方式列出修改前後 LOC，生成檔另計。LOC 只作輔助資訊，不設減量目標；未實作時不虛報前後數字，也不為行數犧牲清楚程度。
